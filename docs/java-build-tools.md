# Java build tools: Maven explained for npm users

In Node, separate tools manage dependencies (`npm`), compile (`tsc`), test (`vitest`) and run scripts (`package.json` `"scripts"`). In Java, **one build tool does all of it**: it downloads dependencies, compiles `.java` → `.class`, runs tests, and packages a runnable `.jar`. Our Spring repos use **Maven**, run through the **Maven Wrapper** (`./mvnw`).

**Versions** (generated with Spring Initializr and run, October 2026): Maven **3.10.0** (via wrapper 3.3.4) · Spring Boot **4.1.2** · Java **25**. Maven 4 is still a release candidate, so we stay on 3.x.

Related: [java-for-ts-devs.md](java-for-ts-devs.md) · [ecosystem.md](ecosystem.md) · [gotchas.md](gotchas.md#maven)

## 1. Maven vs Gradle (and why Maven)

| You know (Node) | Maven | Gradle |
|---|---|---|
| `package.json` | `pom.xml` (XML, declarative) | `build.gradle.kts` (Kotlin code) |
| `dependencies` / `devDependencies` | `<scope>compile</scope>` / `<scope>test</scope>` | `implementation(...)` / `testImplementation(...)` |
| `npm install` | happens automatically on every build | happens automatically on every build |
| `node_modules/` (per project) | `~/.m2/repository` (**one global cache** shared by all projects) | `~/.gradle/caches` |
| `npm run build` / `npm test` | `./mvnw package` / `./mvnw test` | `./gradlew build` / `./gradlew test` |
| `npm run dev` | `./mvnw spring-boot:run` | `./gradlew bootRun` |
| `"scripts"` (anything goes) | **fixed lifecycle** that plugins hook into | task graph you program |
| npm registry | Maven Central | Maven Central (the same repository) |

- **Maven is declarative.** You *describe* the project and Maven runs the same fixed lifecycle for every project. It's verbose but predictable, and it's what most Spring tutorials and enterprise codebases use.
- **Gradle is programmable.** Builds are code, which makes them concise and fast (incremental builds, build cache, daemon). It's the standard for Android and large monorepos, but every build can be a little different and errors are harder to read for beginners.

We chose Maven so you learn Java and Spring without also learning a build language. Moving to Gradle later takes an afternoon ([§14](#14-the-same-project-in-gradle)).

## 2. The Maven Wrapper (`./mvnw`)

You don't install Maven globally. Each Spring repo commits a small script that downloads the exact Maven version the project needs, the first time you run it.

```
mvnw                                   # the script for macOS / Linux / WSL (commit it, keep it executable)
mvnw.cmd                               # the Windows version
.mvn/wrapper/maven-wrapper.properties  # pins the Maven version
```

```properties
# .mvn/wrapper/maven-wrapper.properties (as generated by Spring Initializr)
wrapperVersion=3.3.4
distributionType=only-script
distributionUrl=https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.10.0/apache-maven-3.10.0-bin.zip
```

```bash
./mvnw -v
# Apache Maven 3.10.0 (...)
# Maven home: /home/<you>/.m2/wrapper/dists/apache-maven-3.10.0/...
# Java version: 25.0.4.1, vendor: Eclipse Adoptium, ...
```

The npm analogy is pinning `"packageManager": "pnpm@x.y.z"` and using Corepack: everyone, including CI, builds with the same tool version. Maven itself runs on whatever JDK `JAVA_HOME` points to. For us that's SDKMAN's Temurin 25.

If you get `permission denied: ./mvnw`, run `chmod +x mvnw` and then `git update-index --chmod=+x mvnw` so the executable bit is committed.

## 3. Project layout

Maven is **convention over configuration**: put files in these folders and no configuration is needed.

```
pom.xml
src/
  main/
    java/dev/taskflow/...        ← production code; folders mirror the package name
    resources/                   ← application.yml, db/migration/*.sql (Flyway); copied onto the classpath
  test/
    java/dev/taskflow/...        ← tests, in the same packages as the code they test
    resources/                   ← test-only config
target/                          ← ALL build output (like dist/ + coverage/); git-ignored
  classes/                       ← compiled main code + resources
  test-classes/
  surefire-reports/              ← test results (XML/TXT)
  site/jacoco/                   ← coverage HTML report (once JaCoCo is added)
  taskflow-0.0.1-SNAPSHOT.jar    ← the packaged app
```

"The **classpath**" means the list of folders and JARs the JVM searches for classes and resources: `target/classes` plus every dependency JAR. It plays the role of Node's module resolution. That's why `src/main/resources/application.yml` can be loaded as `classpath:application.yml`.

## 4. Anatomy of a `pom.xml`

POM stands for *Project Object Model*. This is what Spring Initializr generates for Spring Web + Validation, with the empty metadata tags (`<licenses>`, `<scm>`, …) removed:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
	xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
	<modelVersion>4.0.0</modelVersion>                       <!-- POM format version; always 4.0.0 -->

	<parent>                                                 <!-- inherit config + managed versions (§6) -->
		<groupId>org.springframework.boot</groupId>
		<artifactId>spring-boot-starter-parent</artifactId>
		<version>4.1.2</version>
		<relativePath/>                                      <!-- look the parent up in the repository -->
	</parent>

	<groupId>dev.taskflow</groupId>                          <!-- like an npm scope: @taskflow -->
	<artifactId>demo</artifactId>                            <!-- like "name" -->
	<version>0.0.1-SNAPSHOT</version>                        <!-- like "version" -->
	<name>demo</name>

	<properties>                                             <!-- variables, referenced as ${java.version} -->
		<java.version>25</java.version>
	</properties>

	<dependencies>                                           <!-- no <version>: the parent manages them -->
		<dependency>
			<groupId>org.springframework.boot</groupId>
			<artifactId>spring-boot-starter-validation</artifactId>
		</dependency>
		<dependency>
			<groupId>org.springframework.boot</groupId>
			<artifactId>spring-boot-starter-webmvc</artifactId>
		</dependency>

		<dependency>
			<groupId>org.springframework.boot</groupId>
			<artifactId>spring-boot-starter-validation-test</artifactId>
			<scope>test</scope>                              <!-- like devDependencies (§7) -->
		</dependency>
		<dependency>
			<groupId>org.springframework.boot</groupId>
			<artifactId>spring-boot-starter-webmvc-test</artifactId>
			<scope>test</scope>
		</dependency>
	</dependencies>

	<build>
		<plugins>                                            <!-- build steps (§10) -->
			<plugin>
				<groupId>org.springframework.boot</groupId>
				<artifactId>spring-boot-maven-plugin</artifactId>
			</plugin>
		</plugins>
	</build>
</project>
```

| `package.json` | `pom.xml` |
|---|---|
| `"name": "@taskflow/demo"` | `<groupId>dev.taskflow</groupId>` + `<artifactId>demo</artifactId>` |
| `"version"` | `<version>` |
| `"engines": { "node": ">=24" }` | `<java.version>25</java.version>` (the compiler targets Java 25) |
| `"dependencies"` | `<dependencies>` with the default scope |
| `"devDependencies"` | `<dependencies>` with `<scope>test</scope>` |
| `"scripts"` | `<build><plugins>` bound to lifecycle phases |
| `"extends"` in tsconfig | `<parent>` |

**Spring Boot "starters"** are dependencies that bundle a coherent set of libraries together with their auto-configuration. `spring-boot-starter-webmvc` brings Spring MVC, an embedded Tomcat server and Jackson. Since Boot 4, each starter has a matching `-test` starter (JUnit 5, AssertJ, Mockito, MockMvc).

You will **edit the POM by hand**. There's no `mvn add <pkg>`. You find the coordinates on [central.sonatype.com](https://central.sonatype.com) or in the library's docs and paste in a `<dependency>` block. The next build downloads it.

## 5. Coordinates and versions

Every artifact is identified by **GAV**: `groupId:artifactId:version`, for example `org.postgresql:postgresql:42.7.14`. Reversed-domain group IDs prevent the name-squatting problems npm has.

- **`-SNAPSHOT`** marks a work-in-progress version that is allowed to change. A release version (`1.0.0`) is immutable on Maven Central: once published, it can never be republished or deleted. That's stronger than npm's guarantees.
- **There's no lockfile.** Maven has no `package-lock.json`, and it doesn't need one, because the convention is **exact versions only**. You never write version ranges (`^1.2.0` / `[1.2,2.0)`). The Spring Boot parent pins hundreds of library versions, and you pin the rest exactly. The POM *is* the lock.
- To see what can be upgraded: `./mvnw versions:display-dependency-updates` (from the Codehaus versions plugin). In our repos Dependabot opens the upgrade PRs.

## 6. Spring Boot's parent POM and BOMs

Why do the Spring dependencies above have no `<version>`? Because the `spring-boot-starter-parent` contains a giant **`<dependencyManagement>`** section, a list that says "*if* this project uses library X, use version Y". It doesn't add dependencies by itself. It only fixes their versions.

That list is called a **BOM** (Bill of Materials). Spring Boot 4.1.2 tests a set of versions that work together and pins them. Some examples, read with `./mvnw help:evaluate -Dexpression=<property> -q -DforceStdout`:

| Property | Version managed by Boot 4.1.2 |
|---|---|
| `postgresql.version` | 42.7.14 |
| `flyway.version` | 12.4.0 |
| `jackson-bom.version` | 3.1.7 (Jackson 3) |
| `testcontainers.version` | 2.0.5 |
| `maven-surefire-plugin.version` | 3.5.6 |

The npm world has no direct equivalent. The nearest is a monorepo `overrides` / `resolutions` block that's maintained for you and tested as a set.

```xml
<!-- Library managed by Boot: no version needed -->
<dependency>
	<groupId>org.postgresql</groupId>
	<artifactId>postgresql</artifactId>
	<scope>runtime</scope>
</dependency>

<!-- Library NOT managed by Boot: pin an exact version yourself -->
<dependency>
	<groupId>org.springdoc</groupId>
	<artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
	<version>X.Y.Z</version>       <!-- exact version chosen and verified when the repo is built -->
</dependency>
```

To override one managed version (for example after a security fix lands before Boot's next release), set its property:

```xml
<properties>
	<java.version>25</java.version>
	<postgresql.version>42.7.15</postgresql.version>   <!-- overrides Boot's choice -->
</properties>
```

Libraries that are themselves made of many modules (the AWS SDK, Testcontainers) publish their own BOM, which you **import** inside `<dependencyManagement>`. After that, their individual modules don't need versions either:

```xml
<dependencyManagement>
	<dependencies>
		<dependency>
			<groupId>software.amazon.awssdk</groupId>
			<artifactId>bom</artifactId>
			<version>X.Y.Z</version>
			<type>pom</type>
			<scope>import</scope>
		</dependency>
	</dependencies>
</dependencyManagement>
```

## 7. Dependency scopes

| Scope | On the compile classpath? | In tests? | Packaged into the app? | Use for | npm analogue |
|---|---|---|---|---|---|
| `compile` (default) | ✓ | ✓ | ✓ | libraries your code imports | `dependencies` |
| `runtime` | ✗ | ✓ | ✓ | drivers you never import directly (the PostgreSQL JDBC driver) | `dependencies` you never `import` |
| `test` | ✗ | ✓ | ✗ | JUnit, Testcontainers, MockMvc | `devDependencies` |
| `provided` | ✓ | ✓ | ✗ | supplied by the runtime environment (servlet API on an external app server) | `peerDependencies`, roughly |
| `import` | — | — | — | importing a BOM (only inside `dependencyManagement`) | — |

`runtime` is a nice safety net: because the PostgreSQL driver isn't on the compile classpath, your code *can't* accidentally import Postgres-specific classes and has to go through JDBC/JPA.

## 8. Transitive dependencies and conflicts

Dependencies have dependencies. Maven downloads all of them, and they show up as a tree:

```bash
./mvnw dependency:tree
```

```text
[INFO] +- org.springframework.boot:spring-boot-starter-validation:jar:4.1.2:compile
[INFO] |  +- org.springframework.boot:spring-boot-starter:jar:4.1.2:compile
[INFO] |  |  +- org.springframework.boot:spring-boot-starter-logging:jar:4.1.2:compile
[INFO] |  |  |  +- ch.qos.logback:logback-classic:jar:1.5.38:compile
[INFO] |  |  |  |  \- ch.qos.logback:logback-core:jar:1.5.38:compile
...
```

**The big difference from npm:** npm can install *several versions* of the same package side by side in nested `node_modules`. The Java classpath can hold **only one version** of each class. When two dependencies want different versions of the same library, Maven picks one using **"nearest wins"**: the version declared closest to your POM in the tree wins, and among equally deep declarations, the first one wins.

How to stay out of trouble:
1. Let the Spring Boot BOM decide versions (that's what it's for).
2. If two libraries disagree, pin the winner in `<dependencyManagement>` or with a property.
3. Remove an unwanted transitive dependency with `<exclusions>`.
4. Run `./mvnw dependency:tree -Dincludes=groupId:artifactId` to find out who pulls a library in, much like `npm why <pkg>`.

The usual symptom of a conflict is a runtime `NoSuchMethodError` or `ClassNotFoundException`: code compiled against version A is running with version B.

## 9. The build lifecycle

Maven's default lifecycle is an ordered list of **phases**. **Running a phase runs every phase before it.**

```
validate → compile → test-compile → test → package → verify → install → deploy
```

| Phase | What happens (with Spring Boot's defaults) | npm analogue |
|---|---|---|
| `compile` | `javac` compiles `src/main/java` into `target/classes`. Type errors fail here. | `tsc --noEmit` |
| `test` | Compiles tests, runs them with **Surefire** (unit tests named `*Test`) | `npm test` |
| `package` | Builds `target/<artifactId>-<version>.jar`. Spring's plugin turns it into a fat JAR (§11). | `npm run build` |
| `verify` | Integration tests (**Failsafe**, `*IT` classes), coverage checks, format checks | `npm run lint && npm run test:e2e` |
| `install` | Copies the JAR into `~/.m2/repository` so other local projects can depend on it | `npm link` |
| `deploy` | Publishes to a remote repository | `npm publish` |

So `./mvnw package` = validate + compile + test + package. Add `-DskipTests` to skip the tests.

**Plugins do the actual work.** A phase is just a named slot, and plugin **goals** are bound to it. `compile` runs `maven-compiler-plugin:compile`, `test` runs `maven-surefire-plugin:test`, and so on. You can also run a goal directly as `plugin:goal`, without going through the lifecycle:

```bash
./mvnw spring-boot:run          # goal from spring-boot-maven-plugin: start the app (= npm run dev)
./mvnw dependency:tree          # goal from maven-dependency-plugin
./mvnw spotless:apply           # goal from spotless-maven-plugin: format code (= prettier --write)
```

`clean` belongs to a separate lifecycle and deletes `target/`. `./mvnw clean verify` is the classic "build everything from scratch" command used in CI.

Test output to look for:

```text
[INFO] Tests run: 1, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

## 10. Plugins

Plugins are declared under `<build><plugins>`. They're configured with `<configuration>` and attached to phases through `<executions>`. Below are the two our CI depends on. Their versions are pinned when the Spring repo is built (latest at the time of writing: Spotless 3.10.4, JaCoCo 0.8.16).

```xml
<!-- Formatting: `./mvnw spotless:apply` fixes the code, `spotless:check` (bound to verify) fails CI if it's unformatted -->
<plugin>
	<groupId>com.diffplug.spotless</groupId>
	<artifactId>spotless-maven-plugin</artifactId>
	<version>3.10.4</version>
	<configuration>
		<java>
			<googleJavaFormat/>
		</java>
	</configuration>
	<executions>
		<execution>
			<goals><goal>check</goal></goals>      <!-- check's default phase is verify -->
		</execution>
	</executions>
</plugin>

<!-- Coverage: instrument the tests, then write target/site/jacoco/index.html -->
<plugin>
	<groupId>org.jacoco</groupId>
	<artifactId>jacoco-maven-plugin</artifactId>
	<version>0.8.16</version>
	<executions>
		<execution>
			<goals><goal>prepare-agent</goal></goals>   <!-- runs before tests -->
		</execution>
		<execution>
			<id>report</id>
			<phase>verify</phase>
			<goals><goal>report</goal></goals>
		</execution>
	</executions>
</plugin>
```

Compare that with npm, where you'd add `"format": "prettier --write ."` and remember to call it. Maven's version is wordier, but once it's bound to `verify`, *nobody* can forget to run it.

## 11. The runnable "fat" JAR

A `.jar` is a zip of `.class` files plus resources. A normal JAR contains only *your* classes, so running it would need every dependency JAR on the classpath as well. `spring-boot-maven-plugin` **repackages** it into a self-contained JAR with every dependency nested under `BOOT-INF/lib/` (40 JARs for the bare web + validation demo, about 21 MB) and a launcher that knows how to load them.

```bash
./mvnw -DskipTests package
java -jar target/demo-0.0.1-SNAPSHOT.jar              # runs the whole app, no Maven needed
```

That's why the Spring Dockerfile's final stage only needs a JRE plus that one file. In Node, the closest equivalent is bundling an app and its `node_modules` into a single executable.

## 12. Command cheat sheet

| Want to… | npm | Maven |
|---|---|---|
| install dependencies | `npm ci` | *(automatic)*; to pre-fetch: `./mvnw dependency:go-offline` |
| run in dev | `npm run dev` | `./mvnw spring-boot:run` |
| run with a profile | `NODE_ENV=dev npm run dev` | `./mvnw spring-boot:run -Dspring-boot.run.profiles=dev` |
| type-check | `tsc --noEmit` | `./mvnw compile` |
| run tests | `npm test` | `./mvnw test` |
| run one test class / method | `vitest TaskService` | `./mvnw test -Dtest=TaskServiceTest` / `-Dtest=TaskServiceTest#createsTask` |
| everything CI does | `npm run lint && npm test && npm run build` | `./mvnw verify` |
| format | `prettier --write .` | `./mvnw spotless:apply` |
| build without tests | `npm run build` | `./mvnw -DskipTests package` |
| clean build | `rm -rf dist && npm run build` | `./mvnw clean package` |
| who depends on X | `npm why x` | `./mvnw dependency:tree -Dincludes=group:artifact` |
| outdated deps | `npm outdated` | `./mvnw versions:display-dependency-updates` |
| force re-download | `rm -rf node_modules && npm ci` | `./mvnw -U verify` (`-U` refreshes snapshots and missing metadata) |

Useful flags: `-B` (batch mode: no colours or progress bars, use it in CI), `-q` (quiet), `-o` (offline), `-DskipTests`, `-X` (debug output for when a build behaves strangely).

## 13. Maven in CI and Docker

**GitHub Actions:** `actions/setup-java` installs Temurin and caches `~/.m2/repository` for you:

```yaml
- uses: actions/setup-java@v6
  with:
    distribution: temurin
    java-version: "25"
    cache: maven
- run: ./mvnw -B verify
```

The Spring repo's STEPS.md walks through the complete workflow line by line.

**Docker:** copy the POM and wrapper first, download the dependencies in their own layer, then copy the source. A source change then doesn't re-download the internet. It's the same trick as `COPY package*.json` → `npm ci` → `COPY . .`.

```dockerfile
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw -B dependency:go-offline
COPY src src
RUN ./mvnw -B -DskipTests package
```

## 14. The same project in Gradle

So you can recognise it in the wild, here's the demo's build as `build.gradle.kts`:

```kotlin
plugins {
    java
    id("org.springframework.boot") version "4.1.2"
    id("io.spring.dependency-management") version "1.1.7"   // gives Gradle Maven-style BOM handling
}

group = "dev.taskflow"
version = "0.0.1-SNAPSHOT"
java { toolchain { languageVersion = JavaLanguageVersion.of(25) } }

repositories { mavenCentral() }

dependencies {
    implementation("org.springframework.boot:spring-boot-starter-validation")
    implementation("org.springframework.boot:spring-boot-starter-webmvc")
    testImplementation("org.springframework.boot:spring-boot-starter-validation-test")
    testImplementation("org.springframework.boot:spring-boot-starter-webmvc-test")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

tasks.withType<Test> { useJUnitPlatform() }   // Maven's Surefire does this without being told
```

It holds the same information as the POM in about a third of the lines. The trade-off is that this is Kotlin code that runs, rather than data that's read.
